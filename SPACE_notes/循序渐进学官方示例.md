# 用五个具体例子读懂 SPACE 官方示例

**2026-10-25 更新：先按[真实 SPACE 实操](真实SPACE实操.md)运行本机平台，再用本文补充概念。前四课使用真实 VM；第五课 `events` 仍是离线事件解析演示。**

配套脚本：[progressive_examples.py](progressive_examples.py)。当前 Linux 课程直接导入部署的 `/root/SPACE/examples/first_sandbox.py`；对应固定源码见 [first_sandbox.py](../SPACE-source/examples/first_sandbox.py)。

你先扮演“调用 SPACE 的应用开发者”：要申请一个 Linux 工作空间，在里面运行命令，看到结果，最后决定是否删除它。这里的命令由我们写死，不调用大模型；未来 agent 也可以通过工具适配层发起这些请求。

## 先明确：代码运行在两个地方

| 位置 | 具体内容 |
|---|---|
| 客户端，也就是运行教学脚本的地方 | Python 脚本、`config`、`state.json`、保存下来的 `.sse` 记录 |
| 远端 sandbox，也就是 SPACE 创建的 microVM 内 | `sh` 进程、命令打印的内容、`/tmp/space-study/numbers.txt` 等任务文件 |

例如，Python 中的 `directory` 是**客户端记录目录**，命令中的 `cwd: /tmp` 是**guest 内工作目录**。它们即使都位于 Linux 的 `/tmp` 下，也代表不同位置和用途；不要因路径相似就把它们当作同一个目录。

## 怎么使用本材料

先按例子 1→4 理解完整任务；例子 5 放大解释结果处理。每个例子都包含任务、函数、状态变化和预期结果。

### 现在可以在 Windows 上运行的部分

从当前工作区根目录执行：

```powershell
python .\学习材料\progressive_examples.py events
```

这会运行例子 5：把合成的事件输入交给**官方的 `consume_events` 和 `event_frames`**。它不连接 SPACE，不启动 VM，不需要 token。

### 连接真实 SPACE 的部分

例子 1→4 是真实客户端示例，需要先完成 [SPACE 安装及认证](../SPACE-main/docs/installation.md)，在 Linux 客户端环境中使用实际的 `SPACE_API_URL`、`SPACE_DATA_PLANE_URL`、`SPACE_API_TOKEN`，并准备好模板。官方函数中的超时实现使用 Linux 信号机制。

把本工作区的 `SPACE-main/` 和 `学习材料/` 保持为同级目录，在工作区根目录执行后文的 `python3` 命令。脚本没有 pip 依赖，直接导入本地官方 Python 示例，未复制或改写它的 API 实现。

本文列出的实时输出是**预期现象**，本轮没有部署 SPACE 或运行真实 VM。实际运行中生成的 ID、记录目录和模板内容会不同。

## 例子 1：先申请一台工作电脑，还不执行任务

### 具体任务

你希望稍后让 agent 处理文件，因此先申请一个 Linux 工作空间，并确认它能使用。

```bash
python3 学习材料/progressive_examples.py create
```

教学脚本按顺序调用官方函数，下面是阅读用节选；完整可运行版本在配套脚本中：

```python
config = fs.configuration()
# 在客户端新建 directory，并初始化、保存 state。
fs.create_sandbox(config, directory, state)
fs.inspect_run(config, state)
fs.confirm_delete(config, directory, state)
```

这里的 `fs` 就是导入的官方 `first_sandbox.py` 模块。初始化代码可以在配套脚本的 `live_lesson` 中看到。

### 先理解这三个参数

| 参数 | 具体装了什么 | 用途 |
|---|---|---|
| `config` | API 地址、数据面地址、管理 token、模板名 | 知道请求发到哪里、以什么身份调用 |
| `directory` | 例如客户端的 `/tmp/space-lesson-create-某随机串` | 保存这次操作的恢复与诊断记录 |
| `state` | 请求记录、sandbox ID、operation ID、事件文件名等 | 知道自己创建了哪个对象，哪些请求已经发过 |

官方 `save()` 保存 `state`，不会把 `config` 中的管理 token 自动写进 state。

### `create_sandbox` 内发生了什么

发送请求体：

```python
body = {"template": config["template"], "runtime": "fc"}
```

含义是：“按照这个模板，使用 Firecracker 运行时创建环境。”模板提供起始文件系统及运行时配置。

随后经历：

```text
mutation(..., POST, /v1/sandboxes)
    → 保存原始请求及幂等键，再调用 api() 发 HTTP 请求
remember_ids(...)
    → 保存返回的 sandbox_id 和 operation_id
wait_for_state(...operation..., succeeded)
    → 等待创建操作成功
wait_for_state(...sandbox..., running)
    → 等待环境进入运行状态
api(...GET.../processes?limit=1)
    → 检查进程端点是否可用
```

用具体 ID 区分它们，以下只是格式示意：

- `sbx_demo123`：申请到的工作环境。
- `op_demo456`：这一次“创建环境”操作的进度记录。

**为什么要等？** API 接受请求之后，后台还需要准备虚拟机等资源。拿到回执并不意味着电脑已经开机、能接收任务。

### 预期现象与小练习

你会看到客户端记录目录、两个 ID，以及检查接口的 JSON 结果。此时还没有通过教学脚本执行任务命令，进程列表可能为空。

最后会询问是否删除本次 sandbox；输入 `y` 会调用官方删除流程，回车则保留。删除 sandbox 不会删除模板。

第一次阅读时，在 `create_sandbox` 中找到上面的五步，解释每一步检查的是哪个对象。你能分清“创建请求”和“创建出来的环境”，就完成本例目标。

## 例子 2：让刚申请的电脑做自我介绍

### 具体任务

让 sandbox 打印一句问候、显示工作目录，再输出一条演示性的诊断消息。

```bash
python3 学习材料/progressive_examples.py hello
```

这次函数链多了一步：

```python
fs.create_sandbox(config, directory, state)
fs.COMMAND = {
    "command": ["sh", "-c", 'printf "%s\\n" "$GREETING"; pwd; printf "demo warning\\n" >&2'],
    "cwd": "/tmp",
    "env": {"GREETING": "Hello from SPACE"},
    "timeout": "30s",
}
fs.run_command(config, directory, state)
fs.inspect_run(config, state)
fs.confirm_delete(config, directory, state)
```

这里修改的是导入模块的内存变量 `COMMAND`，英文源码文件没有被改写。官方教程也通过修改这个常量定制命令。

### 把请求翻译成人话

- `command`：在 guest 中启动 `sh`，让 shell 解释接下来的字符串。
- `env`：给这次命令设置 `GREETING` 环境变量。
- `cwd`：让这次命令在 guest 的 `/tmp` 目录启动。
- `timeout`：命令执行期限为 30 秒。

`>&2` 表示把这条消息写到标准错误 stderr；默认的 `printf` 和 `pwd` 输出到标准输出 stdout。

### `run_command` 实际做了两段工作

第一段，向管理 API 提交 `COMMAND`：

```text
POST /v1/sandboxes/{sandbox_id}/commands
    → 返回 session_id、process_id 和 attach 信息
```

这时建立的是一次命令会话。第二段，使用返回的 `attach.token` 连接指定数据面地址：

```text
连接 /v1/sessions/{session_id}/events
    → 触发进程启动
    → consume_events(...) 消费输出和退出事件
```

管理 token 用于调用管理 API；attachment token 用于本次命令的连接。官方代码不会把二者混用。

### 预期输出

除 ID 和状态信息之外，会看到：

```text
Hello from SPACE
/tmp
demo warning
Command completed successfully: proc_...
```

stdout 和 stderr 是不同通道，终端合并展示时的先后顺序不必完全一致。

**注意：有 stderr 输出也可能成功。** 这里演示诊断消息后，shell 正常退出，退出码仍为 0。官方 `consume_events` 检查的是退出事件及流错误，而不是“stderr 有没有字”。

小练习：把 `GREETING` 换成自己的名字，再把 `cwd` 换成 guest 中已经存在的 `/`。先预测输出，再运行。你改变的是同一个程序的输入与启动位置。

## 例子 3：连续处理一份数据，理解环境如何保留状态

### 具体任务

模拟一个简短的数据处理任务：

1. 写入两个数字 12、8。
2. 用另一个进程读取并求和，得到 20。
3. 将第二个数字修改为 18。
4. 再启动一个进程求和，得到 30。

```bash
python3 学习材料/progressive_examples.py workspace
```

四步共用一个 sandbox，每步各调用一次官方 `run_command`：

| 步骤 | guest 内执行的具体操作 | 预期输出 |
|---|---|---|
| 1 | 创建 `/tmp/space-study/`，将 `12 8` 写入 `numbers.txt` | 无业务输出，退出码 0 |
| 2 | `read a b < .../numbers.txt`，用 shell 算术求和 | `total=20` |
| 3 | 将 `12 18` 覆盖写入相同文件 | 无业务输出，退出码 0 |
| 4 | 再次读取相同文件并求和 | `total=30` |

这些命令只依赖 guest 中的 `sh` 与 `mkdir` 等基础程序，不需要安装 Python 包或访问网络。完整命令在教学脚本的 `workspace` 分支中。

### 这里具体共享了什么

```text
同一个 sandbox：sbx_某ID
    ├── 命令 1 / 进程 1：写文件 → 退出
    ├── 命令 2 / 进程 2：读文件 → 退出
    ├── 命令 3 / 进程 3：改文件 → 退出
    └── 命令 4 / 进程 4：读文件 → 退出

文件一直位于该 sandbox 的可写文件系统中。
```

前一个进程结束，并不删除它写入的文件。新进程之所以能继续处理数据，是因为它们在同一个工作环境中。

### 为什么不能直接用同一个 state 连调四次？

官方 `run_command` 会检查：

```python
if "command" in state["requests"]:
    raise ValueError("Command was already requested; a new command is not a stream retry")
```

这是**官方教学客户端的请求记录约束**，不是 SPACE 限制一个 sandbox 只能运行一条命令。它防止你把“新的执行”误当成“上次请求的重试”。

配套脚本给每条命令创建独立记录，保留相同 sandbox ID：

```python
step_state = command_record(config, step_directory, state["sandbox_id"])
fs.COMMAND = {"command": ["sh", "-c", shell], "timeout": "30s"}
fs.run_command(config, step_directory, step_state)
```

你会在客户端看到：

```text
/tmp/space-lesson-workspace-随机串/
    state.json                 创建/删除环境的记录
    step-1-write/
        state.json             第 1 条命令自己的请求与 ID
        events-随机串.sse
    step-2-sum/
        state.json
        events-随机串.sse
    step-3-update/...
    step-4-sum-again/...
```

比较这四份 `state.json`：`sandbox_id` 应一致，不同命令的 `session_id` 应不同，幂等键也不同。跨命令延续的是文件状态；本例没有演示进程环境变量或 shell 内存自动延续。

本例最后从顶层记录询问是否删除 sandbox；子目录中的命令记录与事件文件会保留供学习。官方清理函数只清理传入 state 跟踪的文件，不会递归清空这些子目录。

学习目标：解释“一个任务、一个持续工作空间、多次命令执行”的对应关系。这个固定流程还不是完整 agent，只是在展示它将来可使用的执行接口。

## 例子 4：任务打印了日志，却执行失败

### 具体任务

模拟一个检查程序：先打印“开始检查”，再报告错误，最后以退出码 7 结束。

```bash
python3 学习材料/progressive_examples.py failure
```

送入官方 `run_command` 的命令是：

```python
fs.COMMAND = {
    "command": ["sh", "-c", 'printf "starting check\\n"; printf "demo check failed\\n" >&2; exit 7'],
    "timeout": "30s",
}
```

### 预期现象

```text
starting check
demo check failed
...
Stopped: Command did not exit successfully: 7
```

教学脚本本身将以退出码 1 结束，表示它报告了失败；**guest 里的任务进程退出码是 7**。两者不是同一个进程的退出码。

错误从这里产生：

```python
# 官方 consume_events 的关键判断
if kind == "process_exited":
    code = frame.get("exit_code")
    if type(code) is not int or code != 0:
        raise RuntimeError(f"Command did not exit successfully: {code!r}")
```

命令已经启动、打印了输出，仍然会因为退出码非零而被判失败。这也是调用方不能仅凭 HTTP 请求成功就告诉用户“任务完成”的原因。

### 失败后怎么检查和清理

本例在出错后停止，保留 sandbox、请求记录和事件文件，不额外发起删除。记下实际输出的 `Run directory`，用官方入口读取它：

```bash
# 将下面路径替换为本次运行实际打印的目录。
python3 SPACE-main/examples/first_sandbox.py inspect /tmp/space-lesson-failure-实际随机串
python3 SPACE-main/examples/first_sandbox.py delete /tmp/space-lesson-failure-实际随机串
```

继续使用原 API/数据面配置和有效管理 token。第二条命令会询问是否删除。保留记录也适用于其他例子在创建或执行阶段遇到的未知错误。

### 顺便理解 mutation 和幂等键

发送修改请求之前，官方 `mutation` 会先保存请求方法、路径、请求体和幂等键。比如网络中断时，客户端可能没收到响应，但服务端可能已接受创建请求。

因此，“没有收到响应”不能直接翻译成“什么都没发生”。检查保存的记录和对象状态后，才能判断下一步；重新运行整个教学脚本会新建一轮请求，不是在恢复旧的一轮。

学习目标：区分接口请求结果、任务进程结果、教学脚本退出结果；知道失败时该去哪里找证据。

## 例子 5：直接看懂一条输出是如何变成 Python 对象的

这个例子可以先在 Windows 运行。它使用合成数据，仅验证本地事件解析，不验证 API、虚拟机或网络。

```powershell
python .\学习材料\progressive_examples.py events
```

### 具体问题

假设远端进程输出了 `Hello from SPACE`。数据面给客户端传来的数据可以包含这样的 SSE 帧，下面是简化教学输入：

```text
data: {"type": "stdout", "data_base64": "SGVsbG8gZnJvbSBTUEFDRQo="}

data: {"type": "process_exited", "exit_code": 0}

```

两帧之间的空行用于分隔事件。`data_base64` 是编码后的输出字节；客户端需要解码，才能得到原始文本。

### 官方函数如何分工

```text
response 的字节行
    ↓ event_frames(response, transcript)
收集 data: 字段，遇到空行组成一帧，再用 json.loads 变成字典
    ↓ consume_events(response, transcript, stdout, stderr)
根据 type 分流：输出、错误、退出
    ↓
base64 解码 → 写入 stdout / stderr
或检查 process_exited.exit_code
```

`event_frames` 同时把原始输入写入 transcript，便于之后对照和排障。这里 transcript 是内存缓冲区；真实运行时是客户端记录目录中的 `.sse` 文件。

### 脚本运行的三种情况

| 教学输入 | 你会看到的判断 | 原因 |
|---|---|---|
| stdout + stderr + exit 0 | `SUCCESS` | 正常退出，诊断输出不自动等于失败 |
| stdout + exit 7 | `REJECTED` | 任务进程退出码不为 0 |
| 只有 stdout，没有退出事件 | `REJECTED` | 无法确认命令正常完成 |

第三种输入里 stdout 帧本身完整，只是缺少退出事件；它与“最后一帧被截断”是两个不同问题。

小练习：先看 `event_lesson`，自己预测这三种输入的结果，再运行核对。然后进入官方函数，找出对应判断的位置。

## 最后把主要函数连起来

| 官方函数 | 在例子中承担的具体工作 |
|---|---|
| `configuration` | 从环境变量读取连接地址、管理 token 与模板，验证配置 |
| `save` | 将本轮请求记录保存在客户端 |
| `api` | 添加认证头、发送 HTTP 请求、处理 JSON 和 HTTP 错误 |
| `mutation` | 保存修改请求及幂等键，再调用 `api` |
| `remember_ids` / `require_id` | 保存和检查 sandbox、operation、session、process ID |
| `wait_for_state` | 轮询等待期望状态，遇到失败状态及时停止 |
| `create_sandbox` | 申请环境并等待可用 |
| `run_command` | 提交命令会话，再连接数据面启动和读取命令 |
| `event_frames` / `consume_events` | 拆分事件、还原输出并检查退出结果 |
| `inspect_run` | 查询当前环境及操作等状态；其中进程列表表示当前运行的进程 |
| `confirm_delete` / `delete_sandbox` | 询问是否清理、发起删除并等待删除操作成功 |
| `cleanup_transcripts` | 删除传入 state 跟踪的客户端事件文件 |

阅读时可以先跳过 `deadline`、`NoRedirect` 等辅助实现；等到上表的调用链清楚后，再读它们怎样限制超时、避免令牌经代理或重定向发往其他位置。
